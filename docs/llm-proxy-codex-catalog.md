# Codex Model Catalog

Backplane keeps the generic OpenAI-compatible model list and Codex discovery
separate:

* `GET /v1/models` is the ordinary OpenAI-compatible list used by general API
  clients.
* `GET /v1/codex/models` is the rich Codex remote model catalog. It returns the
  current Codex `ModelsResponse` shape, with a top-level `models` array and
  model metadata such as reasoning efforts, context window, visibility, and
  priority.

For example, an enabled entry may produce:

```json
{
  "models": [
    {
      "slug": "deepseek-flash",
      "display_name": "DeepSeek Flash",
      "description": null,
      "supported_reasoning_levels": [],
      "shell_type": "unified_exec",
      "visibility": "list",
      "supported_in_api": true,
      "priority": 30,
      "context_window": 131072
    }
  ]
}
```

The actual response includes the remaining fields required by the current
Codex `ModelInfo` contract; the example is abbreviated for readability.

## Configure the allowlist

Open the admin endpoint and choose **Llama -> Codex Catalog**. Catalog entries
are an explicit allowlist: a provider model discovered or created in Backplane
does not appear in Codex until an operator adds and enables an entry.

For an existing model, set:

* **Codex model ID** to the public slug Codex will send;
* **Routing target** to an existing routable `provider/model` (or an existing
  Backplane model alias);
* an optional display name, description, priority, context-window override,
  and comma-separated reasoning efforts.

The routing target must resolve to an enabled provider model with an enabled
OpenAI Responses surface. This is also the route used when a request to
`POST /v1/responses` contains the public Codex model ID. Provider model IDs are
therefore allowed to differ from public Codex IDs, for example:

```text
Codex ID:       deepseek-flash
Routing target: deepseek/deepseek-v4-flash
```

Third-party and local models use the same flow. First configure the provider and
its model in **Llama -> Providers**, enable an OpenAI Responses API surface for
that provider, then expose the route in the Codex Catalog page. This supports
OpenAI-compatible DeepSeek, Mistral, vLLM, and custom providers without a
provider-specific list. Native-only Anthropic or Google surfaces are not
eligible for this endpoint because Backplane does not translate their protocols
into Responses requests in the catalog adapter.

The catalog page shows disabled entries, invalid routes, deterministic priority
ordering, and a raw preview generated by the same serializer as the HTTP
endpoint. Disabled entries and entries whose provider or Responses route is no
longer available are omitted from `GET /v1/codex/models`.

Canonical model metadata is used first. Generic catalog metadata is applied next,
then explicit context-window or reasoning overrides win. Provider-specific
normalization supplies the remaining fields. Context values must be positive,
and reasoning efforts must be non-empty values supported by the current Codex
schema (including provider-defined custom names); invalid values are rejected
before saving.

## Codex configuration

The discovery feature is enabled by Codex itself:

```toml
model = "gpt-6.1-sol"
model_provider = "backplane"

[model_providers.backplane]
name = "Backplane"
base_url = "https://backplane.gsmlg.net/v1"
model_catalog_url = "https://backplane.gsmlg.net/v1/codex/models"
env_key = "BP_TOKEN"
wire_api = "responses"
requires_openai_auth = false

[features]
api_key_model_discovery = true
```

`api_key_model_discovery` is a Codex-side setting. Backplane cannot enable it
inside an externally started Codex app-server.
